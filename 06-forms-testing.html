Forms and project checks

Finish the contact page, then check the site as a visitor would. Record what really happens.

A form is a place for a visitor to enter information

You have probably filled in a sign-up or search form. A field is an area where you type or choose a value. A label tells you what belongs there. You will make three fields: name, email and message.

Start with the visible form. Check that each label matches its field before adding the provided checking helper. This lesson can be split into two sessions: making the form, then testing and preparing your project.

Why use a contact form?

A form guides a visitor through the information the client needs: who they are, how to reply and what they want to say. Clear labels reduce guessing. A linked label also gives assistive software the field’s name and makes the label itself a larger clickable target.

Input checks can catch a missing message or mistyped email before a visitor continues. That saves frustration, but it does not prove the information is true. Your front-end prototype practises this experience; a connected service or back end would be needed to deliver the message.

1. Build a labelled form

Replace the content inside main in contact.html with this. Keep the rest of that page.

contact.html — replacement main content

<h1>Contact Alex</h1>
<p id="form-note">Practice form: use made-up details.
  Nothing will be sent or stored.</p>
<form id="contact-form" aria-describedby="form-note">
  <label for="visitor-name">Name (required)</label>
  <input id="visitor-name" name="visitor-name" type="text" required>

  <label for="visitor-email">Email (required)</label>
  <input id="visitor-email" name="visitor-email" type="email" required>

  <label for="visitor-message">Message (required)</label>
  <textarea id="visitor-message" name="visitor-message"
            rows="5" required></textarea>

  <button id="check-form" type="button">Check practice form</button>
  <p id="form-result" role="status"></p>
</form>

A label explains a field. Its for value must exactly match the input’s id. Clicking the label should focus the field. name identifies a field’s data if a real form is later connected to a service.

required is a Boolean attribute: its presence makes a value compulsory. type="email" asks the browser to check email format, not whether the address exists. A textarea holds multiple lines. Placeholders are not a replacement for labels.

Append these styles to your CSS file:

Check the form before the helper

  1. Save Contact and open its integrated preview.
  2. Click the word Email. The email field should receive the text cursor.
  3. Type a made-up address. Check that you can also type several lines in Message.
  4. Use Tab to move through the fields. Each focused field should have a visible outline.

The check button will not do anything yet. That is the next step. Typing into a field, checking a value and sending a message are three separate things.

2. Check inputs without sending anything

The button uses type="button", so it does not submit data. A small provided JavaScript helper will ask the browser to check the fields. Understanding JavaScript is an optional extension; focus on the HTML and testing.

  1. Create a js folder beside css.
  2. Create form-demo.js inside it and add the helper below.
  3. Add <script src="js/form-demo.js" defer></script> inside the head of Contact only. defer waits until the HTML has been read.

js/form-demo.js — provided practice helper

const form = document.querySelector("#contact-form");
const result = document.querySelector("#form-result");

// Keep this practice form local, including keyboard submission.
form.addEventListener("submit", function (event) {
  event.preventDefault();
});

document.querySelector("#check-form").addEventListener("click", function () {
  result.textContent = "";
  if (form.reportValidity()) {
    result.textContent = "Inputs pass the browser checks. Nothing was sent.";
  }
});

form.addEventListener("input", function () {
  result.textContent = "";
});

If you prefer to leave JavaScript for later, inspect and test the working practice form. Your own form’s fields will still display, but its check button needs the helper to respond. There is no sending service in this example.

Try it

  1. Leave all fields empty and press Check practice form.
  2. Enter a made-up name, then not-an-email as the email. Check again.
  3. Use learner@example.com, leave the message blank and check.
  4. Add a short message and check. Passing inputs should show “Nothing was sent”.
  5. Use Tab to move through the links and fields. Look for visible focus.

Expected result: missing or malformed inputs trigger browser messages. Valid inputs pass local checks. No email is sent and no message is saved.

Why test with other people?

You know where you put everything; a new visitor does not. Asking someone to find a product or use the contact form can reveal confusing wording or a link you missed. Testing during development helps you fix small problems before they appear across all five pages.

Keep real results so you can show what improved. A useful test record helps you and your client understand what works, what changed and what still needs attention.

4. Prepare the full project

  • Content: at least five pages, with meaningful information about the client, catalogue/products, news, prominent latest work and a contact form.
  • Performance: resize/compress large images appropriately; avoid unnecessary downloads. Check the actual image quality and loading result.
  • Search: give each page a useful title, clear headings and descriptive links. A short, unique meta description can summarise each page. These help describe content; they do not guarantee search rankings.
  • Feedback: ask at least three people to use the site. Record questions, specific feedback and improvements.
  • Review: revisit each client requirement. Explain what is met, partly met or still needs work. Separate site improvements from improvements to your own way of working.

5. Publish and hand in

A browser displays the site. A web server serves its files online. A hosting provider supplies that service. The live URL is the address others can visit.

  1. Use the publishing route agreed in class. The brief suggests tiiny.host or GitHub Pages; the official GitHub Pages quickstart explains that route.
  2. Upload the complete website folder, keeping paths and filenames intact. Keep personal information out of the published site.
  3. Open the live URL and repeat your key tests. A local file:/// address does not count as publishing.
  4. Capture live screenshots with the address bar. Explain the publishing steps in section 4.2.
  5. Hand in your evidence Word document, proposal PowerPoint, website ZIP and live URL. The ZIP contains website files and assets, not your Word document or slides.

Final self-check

Does a valid email field prove a message was sent?

No. Browser validation only checks inputs. Sending messages needs a connected service or back end. Describe the prototype honestly in your client-requirements review.

Can I hand in the reference site as my project?

Use it for practice and comparison. Your assessed work needs your own client research, proposal, wireframes, content, decisions, testing evidence and explanations.

Spot the error

Why does clicking the label not focus the email field?

The field appears and you can type into it directly, but clicking “Email” does not move the cursor into the field.

Broken example — find the mistake

<label for="email">Email</label>
<input id="visitor-email" name="visitor-email"
       type="email" required>
Need a hint?

Compare the label’s for value with the input’s id value.
